# Factorized step labels v1: is a step's causal weight separable from its validity?

Date: 2026-10-08. Experiment ID: `factorized_step_labels_v1`. Predecessors: §21.17 (ReProbe trajectories), §21.18 (input conventions), §17 (WikiProfile patching discipline).

This plan covers only the two causal factors, **downstream risk** and **necessity**. Validity and cause (the 9-category taxonomy of `docs/research_direction_s3.md`) are a separate judge-only task.

## 1. Why

Every verifier so far predicts one binary label per step: correct or erroneous. That label mixes at least three things:

* whether the step is locally valid;
* whether the final answer actually depends on it;
* whether continuing from it makes a later error more likely.

A wrong step that the model routes around is harmless. A valid step that pushes the model toward a fragile path is not. If these factors come apart, a single "incorrect" label is the wrong target, and part of the probe's ceiling may come from asking it to predict a mixture.

v1 measures the two causal factors on the model's own reasoning, per fork point, and asks whether they are measurable at all with a pilot budget. It does not yet ask whether a probe can read them.

* **Downstream risk.** Does continuing from the real step i lead to more wrong final answers than the model's own alternatives at the same point?
* **Necessity.** If step i's internal states are replaced by a content-free baseline, how much less likely does the model find the continuation it actually wrote?

## 2. Conditions

A **fork point** is (problem, steps 1..i-1) from a ReProbe Qwen3-8B trajectory, with step i the scored step.

**Context.** The trajectories were generated by ReProbe under their own prompt, not under `chat_prompt`. Decoding the released `input_ids` gives it exactly: Qwen3's chat template, non-thinking, ReProbe's step-format instruction ("- Step k: ..." one per line, then "<Answer>: ..."), with "Reasoning Steps:\n" opening the assistant turn. Continuing this text under `chat_prompt` would put the model in a context it never wrote under. So v1 uses the recorded context:

* `reprobe_prompt(question)` is pinned as a literal in `src/onpolicy/prompts.py`;
* the split builder asserts, for every selected row, that it tokenizes to the released prompt ids;
* the reply is taken as the released token ids, never re-tokenized.

Step boundaries come from ReProbe's `claims[*].aligned_token_ids`. A trace is used only if the claims tile the reply contiguously and every claim decodes byte-identically to its sentence.

**Track 1: downstream risk, by free generation.**

| condition | context | samples |
|---|---|---|
| `A` | prompt + steps 1..i (real step i) | k continuations to the end |
| `C_j`, j = 1..m | prompt + steps 1..i-1 + a sampled step i | m alternatives, then k continuations each |

* An alternative step is sampled from the prefix with no reference to the original text and stops at its first newline token, which is how the format ends a step. Its token ids are used as generated.
* An alternative may equal the original step or be the answer line. Both are kept, because they are part of the model's own variation at the fork, and both are flagged.
* A deletion condition is not included. An autoregressive model has no state for "a step is missing", so delete-and-regenerate is the `C` condition.

**Track 2: necessity, by activation patching.** The original trajectory, unmodified (prompt, steps 1..i, real steps i+1..end, real answer line, first `<|im_end|>`), is teacher-forced. The continuation is everything after step i.

| condition | step i's states at `hidden_states[L]` | role |
|---|---|---|
| `clean` | unpatched | reference log-probability |
| `self` | step i's own clean states | **no-op gate** |
| `mean` | position-matched reference mean | the necessity measurement |
| `rand` | random directions, norm-matched per position | content-free reference, not a no-op |

* The patch reuses `make_span_patch_hook` from `src/analysis/das_span.py` on `model.model.layers[L-1]`. Every block above L recomputes its K/V from the patched span within the same forward, as in das_span.
* The patched span is step i's content: the step line minus its "- Step k:" marker, through the trailing newline token. The marker carries the step count that every later marker depends on, so ablating it would inflate necessity uniformly.
* **Position-matched mean.** Reference steps come from 300 finished `calib` trajectories, a split disjoint from the pilot. They are encoded under the same context. For content offset j, the baseline is the mean reference state at offset j over steps long enough to have one. Offsets with fewer than 20 reference steps use the tail mean. The final (newline) token gets the mean of reference final tokens, because the boundary token is a different kind of position.
* **Landing check.** In every patched forward, a pre-hook on block L reads its input on the span and must match the patch exactly. In one clean forward per fork, the output of block L-1 must equal `hidden_states[L]`, which pins the layer-index convention.

**Layer.** The primary layer is `hidden_states[35]`, the project's readout layer. Qwen3-8B has 36 blocks, so a patch at 35 is read by **one** block. Whatever blocks 0 to 34 already moved from step i into later positions survives the patch.

The prespecified prediction is therefore that L35 necessity is near zero for most forks. That would be a property of the layer, not evidence that steps are bypassed. Layers 1, 9, 18 and 27 run as secondary diagnostics on the same forks. At L1 only block 0 has read the span before the patch, so it is the closest to "remove step i's content". Track 2 costs teacher-forced forwards only, so the sweep is cheap.

**Shared settings.**

* Qwen/Qwen3-8B, revision b968826, bf16.
* Sampling T = 1.0, top-p 0.95, top-k 50. The reply length cap is 4096 tokens, counted from the start of the reply, prefix included.
* Pilot m = 4, k = 8.
* Seeds: generation seed 42; the `rand` directions are seeded per fork.

## 3. Sources and evaluation

**Trajectories.** `rediska0123/train_prm800k_Qwen3-8B_finished` (rev 13cb942) supplies text, token ids and DeepSeek-R1 labels. Self labels come from `JingweiNi/train_prm800k_Qwen3-8B_finished_self_annotate` (rev 672bf94). Both arrive through the frozen v2 manifest (§21.17), whose split assignment already removes the 752 ProcessBench-overlap problems.

**Pilot fork set (frozen before any GPU job).** 30 forks from the v2 `dev` split, one per problem:

| stratum | levels |
|---|---|
| validity of step i | `correct`: both annotators label it correct; `incorrect`: both label it the trace's first error |
| position | `early`, `mid`, `late`: thirds of the trace's step lines |

That gives 6 cells of 5 forks.

* **The GSM8K/MATH stratum is dropped.** Every ReProbe trajectory is a PRM800K problem, so the source is MATH-only. Recorded as a deviation.
* **Prefix.** Steps 1..i-1 are labeled correct by both annotators in both validity levels. The contrast is then the step, not a prefix that has already gone wrong.
* **Eligibility.**
  * The trace finished with an "<Answer>:" line and `<|im_end|>`.
  * The alignment checks above pass.
  * The gold answer is a `\boxed{}` in the ground-truth solution.
  * Step i is a "- Step k:" line, not the answer line.
* **Selection.** Within each cell, forks are picked by sha1(trace_id, step) order.
* **Frozen artifact.** The split JSON carries prompt and reply token ids, spans, labels, the trajectory's own graded outcome, source checksums and its own sha256.

**Full-run fork set (2026-10-08, approved after the pilot).** 501 forks from the v2 `train` split, one per problem, frozen as `fork_split_full.json`:

* **Incorrect steps**: 100 per position, from the 770 problems with an eligible first error.
* **Correct steps**: 67 per position, from "hard" problems only. A problem is hard if some ReProbe trace of it has a step labeled wrong by either annotator, or a wrong final answer. This rule drops 43,518 easy correct-step candidates. In the pilot, correct steps on such problems almost never produced a wrong continuation (err(A) 0.008), so they carry no risk signal.
* The incorrect cells are filled first, so the scarce strata get their problems.
* The fork set is disjoint by problem from the pilot (`dev`) and from the reference set (`calib`).

**Scope limit.** ReProbe's replies are capped at 256 tokens, and only finished traces are eligible, so every fork comes from a problem the policy solved, rightly or wrongly, in at most 256 tokens. Continuations here are capped at 4,096 and are never truncated by that limit.

**Grading.** The project grader is reused: `is_equiv` and `answer_key` from `src/eval/math_grade.py`, after the grader fix of §21.10 and the shared answer identity of §21.13.

* ReProbe-format replies end with "<Answer>: X", not `\boxed{}`. `extract_final_answer` would then fall back to the last number, so "3/4" would be read as "4". A thin extractor therefore reads the last "<Answer>:" line, unwraps a `\boxed{}` or `$...$` inside it, and passes the string to `is_equiv`. Without that line, it defers to `extract_final_answer`. No equivalence logic is new.
* Within a fork, all continuations sharing an `answer_key` get one grade, which is correct if any member matches. This is the §21.13 harmonization.
* Unparseable and length-capped continuations count as errors.

## 4. Metrics and contrasts

**Downstream risk, per fork.**

* err(A) and err(C_j) are the fractions of k continuations graded wrong.
* `risk_diff` = err(A) - mean_j err(C_j). Primary.
* `risk_pct` = the fraction of alternatives with err(C_j) < err(A), plus half the ties.
* `risk_z` = `risk_diff` / sd_j err(C_j), when that sd is above 0.
* A bootstrap SE over continuations and alternatives.

**Necessity, per fork and layer.**

* `nec_sum` = log P(continuation | clean) - log P(continuation | mean). Positive means step i was needed.
* `nec_tok` is the same per continuation token.
* `nec_next` covers step i+1 only, and `nec_ans` the answer line only.
* The same quantities for `rand`, and `self` for the gate.

**Pilot amendment (2026-10-08, after seeing pilot data).** The first continuation token is predicted at the span's last position, which is the patched state itself. Its drop is a direct readout of the overwritten state, not dependence carried by attention. On the 6 last-step forks, that one token ("<" of "<Answer>") carried the whole L35 effect, about 29 nats. All necessity segments now start one token after the span, and that token's drop is reported separately as `nec_boundary`. The change is recorded here because it was made after looking at the data. The random-patch reference in the pilot still includes the token, because its per-token log-probs were not stored. They are stored from now on.

**No-op gate (blocks every necessity number).** At each layer, over the 30 forks:

* median |self Δ log P| ≤ 0.01 nats on the continuation sum, and the maximum ≤ 0.1;
* every landing check passes.

The precedent is §17, where the self-patch control gave +0.02 against effects of 1.34. If the gate fails, track 2 is reported as broken and nothing downstream is interpreted.

**Track-1 sanity (blocks interpretation of risk).** err(A) should be higher for the `incorrect` stratum than for `correct`. If first errors labeled by both annotators do not raise the continuation error rate, the generation or grading path is suspect before the hypothesis is.

**Full-run reading.**

* **Settings.** m = 8 and k = 8 (72 continuations per fork). Necessity is read at L9 and L18 (primary); L1, L27 and L35 stay as diagnostics.
* **Necessity measures.** Necessity is per token, split into step i+1 and the steps after it.
* **Factor relations.** Pairwise relations between validity, `risk_diff` and per-token necessity. Each is reported two ways: as a Spearman correlation, and as a partial Spearman controlling for log continuation length and relative position. Both carry 95% fork-bootstrap intervals; one fork per problem, so this is a problem bootstrap.
* **Counts.**
  * Incorrect steps with err(A) = 0, i.e. bypassed errors.
  * Correct steps with any wrong continuation.
  * The share of forks with `risk_diff` above twice its SE.
* **Factorization.** The factors count as separable if `risk_diff` and necessity are each only partly predicted by validity, that is, if the validity correlation of each has a 95% interval below 0.7. They also need to differ from each other: the partial correlation between `risk_diff` and necessity must not be near 1.
* **Grader gap.** The residual math_grade miss rate (about 2% on traces both annotators call error-free) stays a known limit.

**Pilot reading.** With 30 forks this is descriptive. It answers four questions:

1. Do the gate and the sanity check pass?
2. How noisy is `risk_diff` at m = 4, k = 8? The per-fork SE, compared with the spread across forks, sizes m and k for the full run.
3. Does necessity grow from L35 toward L1, as the one-block argument predicts? Which layer gives a usable spread?
4. Across forks, how do validity, `risk_diff` and `nec_sum` relate? Spearman correlations and the 2 x 3 cell means, with no significance claims.

A full-scale design is proposed only after these are reported.

## 5. Execution

1. `scripts/factorized_step_labels/build_fork_split.py` writes `fork_split_v1.json` (30 forks) and `reference_set_v1.json` (300 calib traces for the mean). It reads the ReProbe parquet and the v2 meta files. It is run and inspected locally before any GPU job, then shipped beside a code snapshot (`scripts/tamia/snapshot.sh`, no commit).
2. Track 1, `scripts/factorized_step_labels/track1_generate.py`: one H100:4 node. Forks are sharded across the 4 GPUs in-node (`CUDA_VISIBLE_DEVICES`). Each fork runs 1 alternative-sampling call plus 1 + m continuation calls. The pilot is 30 x (1 + 4) x 8 = 1,200 continuations plus 120 sampled steps.
3. Track 2, `scripts/factorized_step_labels/track2_patch.py`: one H100:4 node. GPU 0 first computes the reference means at L ∈ {1, 9, 18, 27, 35}. Then 4 shards run clean, self, mean and rand at every layer. That is 30 x 5 x 4 teacher-forced forwards.
4. `scripts/factorized_step_labels/summarize_pilot.py` (CPU, after both) merges the shards, applies the gate and the sanity check, and writes `summary.json` and `summary.md`.
5. Shards go to `$SCRATCH/cot_mech/factorized_step_labels_v1/`; the split, the merged outputs and the summary go to `/project/aip-azouaq/$USER/cot_mech/factorized_step_labels_v1/`. Results are copied to `results/factorized_step_labels_v1/`.
6. Stop after the pilot and report. No run beyond 30 forks without confirmation.
7. Full run (confirmed 2026-10-08): `bash slurm/submit_factorized_step_labels.sh <snapshot> full`.
   * Track 1 runs on 4 H100:4 nodes, as 16 shards with walltime 1:30. `RESUME=1` continues a shard cut by the walltime.
   * Track 2 runs on one node, followed by the summary. Outputs go to `/project/aip-azouaq/$USER/cot_mech/factorized_step_labels_v1/full/`.

## 6. Out of scope

* Validity and cause labels, the judge-only factorization task.
* Training probes on the new factors.
* ProcessBench evaluation. The PB exclusion keeps it possible later.
* PRM800K human-written solutions, which are off-policy text for this model.
* A deletion condition, for the reason given in §2.
* Scaling past the 30-fork pilot.
